Graph layout for ontologies

Tidy Stress and Mycelium

Two layouts that draw ontologies with far fewer crossed links and fewer links running through classes than the widely used open-source layouts, even when those are tuned, and an auto mode, Best Read, that picks the better of the two layouts for a given ontology.

An ontology diagram is only useful if a reader can follow each link from one class to another. Two things make that hard: links that cross, and links that pass under a class box, so that two unrelated classes look connected. General-purpose layouts reduce the first only as a side effect and do little about the second. Tidy Stress and Mycelium are built to minimise both, without letting the drawing sprawl.

Below, a 179-class banking ontology: eleven class hierarchies joined by relationships. On the left is the open-source layout that scored best on this ontology; on the right, ours. Mark problems shows every crossing (dot) and every link that runs through a class (red).

The two layouts

Tidy Stress up to a few dozen classes

Places classes so that straight-line distances match how many links apart they are, then tidies the drawing: it moves classes to remove crossings, to take them off links that run through them, and to shorten long links, keeping a move only if nothing else gets worse.

Mycelium large and hub-heavy ontologies

Draws groups of closely linked classes as compact pods joined by longer threads. Every hub gets a ring wide enough for all its neighbours, and classes with a single link fan out around the class they hang from, with room for the link's label.

Auto mode: Best Read

Best Read applies whichever of the two layouts reads better for a given ontology. It runs Tidy Stress and Mycelium, scores both drawings for readability, and keeps the better one. Above 100 classes it runs Mycelium alone: at that size Mycelium drew far fewer crossings and links through classes in every test, and running both would double the time. It changes no setting inside either layout; it only chooses between their results.

Tidy Stress on a typical ontology

Most ontologies people draw have 10 to 30 classes. There the open-source layouts are already decent, and the difference is in the details: fewer crossings, no link through a class, links of even length.

Mycelium on the hardest case: hubs

A 53-class clinical record in which three classes link to almost everything. No placement can untangle this fully. Mycelium gives each hub a ring of room so that its links stop running through other classes, at the cost of a larger drawing.

What they give up:

  • They are not the most compact. cose and dagre pack tighter; cose does so by letting links run through boxes.
  • Mycelium's threads between pods are long by design.
  • They are slower than the native libraries, though within about a second and a half at every size tested.

Against tuned settings, on standard measures

A readability score designed alongside the layouts it ranks can flatter them. So this comparison changes two things:

  • Tuned settings. Each open-source library tried several settings and seeds, its default run included, on each of the 15 graphs up to 179 classes. It kept the run with the fewest crossed links plus links through classes, a choice made on standard counts rather than on our score. Layered layouts were given subclass links oriented parent to child. The settings tried are listed under Benchmark method.
  • Standard measures. Besides crossings, links through classes and area, four measures from the graph-drawing literature that our layouts do not optimise directly: how faithfully straight-line distance follows graph distance (normalised stress), how even the link lengths are, the angle at which links cross, and the smallest angle between the links at a class (angular resolution).

What we value. These layouts are for ontologies, not for graphs in general, and that changes which measures count:

  • Crossed links and links through classes come first. Each can make a reader follow the wrong link.
  • Crossing angle and angular resolution come next. A shallow crossing is harder to follow than a square one, and links that enter a class from almost the same direction are hard to tell apart.
  • Area matters, but less than both.
  • Distance fidelity and even link lengths are not goals. A business ontology often joins several domains, such as sales, finance and operations, each with classes linked back to shared classes like Person or Organization. The link says that they are related; drawing them close would pull the domains into each other. Keeping each domain together, even when that makes a link to a shared class long, is what Mycelium is for. These two measures are shown for completeness, not counted.

What holds up. Ours draw the fewest crossed links: over the 15 graphs, Best Read draws 550 and Mycelium 542, against 960 for tuned neato, 971 for tuned WebCola and 1,070 for tuned sfdp. They also draw fewer links through classes than every tuned layout but one, and they share the best angular resolution with WebCola. Tidy Stress still ranks first on our readability score, and is first on that score on 12 of the 15 graphs.

What does not.

  • Tuned neato draws fewer links through classes (81 against Best Read's 183) by spreading out: its median drawing takes twelve times the area of Best Read's. Tuning made its readability score worse, not better.
  • On distance fidelity and even link lengths, both layouts rank in the bottom half; ELK stress, WebCola, fcose and d3-force are better. That is by design, as explained above, but a reader who values those measures should know it. Weighting all seven measures equally, WebCola comes first at 4.9 and Tidy Stress second at 5.1.
  • Crossing angle is a weaker point: Tidy Stress ranks 4.4 and Mycelium 6.6, behind fcose and WebCola. Bending links slightly near a crossing could square it up; see Experiments.
  • Which measures matter most for reading an ontology is a judgement backed by Purchase's studies of crossings, not a study of our own.
  • Tuning brought the open-source layouts closer: tuned WebCola, sfdp and neato draw 13%, 17% and 34% fewer crossings than at their general settings.

How the layouts work

Steps both layouts share

  1. Target distances. Every link gets a target length (170 px by default; subclass links slightly shorter; a link with a label is long enough for the label). The target distance between any two classes is the length of the shortest path of links between them.
  2. Placement. Classes are placed so that straight-line distances match the target distances as closely as possible (stress majorization), starting from a pivot-MDS placement, which gives the same result every time. Overlapping boxes are then pushed apart.
  3. Tidy-up. Four local searches run in this order. Each keeps a move only if it adds no crossing, no link through a box and no overlap:
    1. Swap two classes, or move one beside a neighbour, when that reduces crossings.
    2. Move a class off links that run through it.
    3. Pull classes toward their neighbours to shorten long links, then shrink the whole drawing evenly as far as the boxes allow.
    4. Move classes off links once more.
    Without these steps (placement alone, as in Graphviz neato) a drawing has typically 2–3× as many links through classes and about twice as many crossings.
  4. Leaf fanning, when used. Classes linked to a single other class are left out of placement and put back last.
    • Each is placed around its neighbour by trying 48 directions at the nearest free distances.
    • The chosen spot minimises 100 × crossings + 80 × links touching the box + distance.
    • Each keeps at least max(40 px, label width + 16 px) from its neighbour, so the link's label fits.
    • Any whose link ends up crossed or touched is placed again.
    Ontologies have many classes of this kind, such as leaf subclasses.

Tidy Stress

Tidy Stress tries four settings of the shared steps within 1.5 seconds, scores each drawing, and keeps the most readable. The settings differ only in their options, not in the order of the steps:

  • random starts instead of the pivot-MDS start, keeping the start with the fewest crossings;
  • the pivot-MDS start, then moving any single-link class to a better free spot if there is one;
  • leaf fanning, with extra room round classes that have many links (the hub rings described below);
  • leaf fanning alone.

From 31 to 60 classes it tries three of these, and above 60 only the second, because sharing the time between settings leaves each too little time to tidy up.

Mycelium

  • Pods. Louvain community detection finds groups of closely linked classes. Links inside a group get 0.85× the target length and links between groups 1.6×, so placement separates the groups while still letting a class shared by two groups sit between them.
  • Hub rings. A link at a class with k neighbours is at least Σ(neighbour width + 20 px) / 2π long, the radius of a ring that holds all the neighbours side by side. On the clinical-record graph this rule alone cuts links through classes from about 80 to about 43.
  • Leaf fanning, as above.
  • Target length. 260 px from 100 classes.
  • Limits. It needs at least 8 classes and has a 1 s budget.

How readability is scored

Tidy Stress (between its settings) and Best Read (between the two layouts) choose the drawing with the lowest score. The score adds up:

  • 10 for every pair of crossed links;
  • 8 for every link that runs through a class box;
  • 2 for every pair of links that come within 30 px of each other;
  • 40 for every pair of overlapping boxes;
  • a tenth of the mean link length, plus a penalty when the mean exceeds 350 px;
  • a penalty for area beyond eight times the total area of the boxes, growing with the number of classes;
  • 25 for every multiple, beyond 1.8, of the median link length by which a link is longer.

The last two terms matter. A layout can avoid crossings by pushing classes far apart or by stretching a few links across the whole drawing. Without those terms, such drawings would win on crossings alone even though they are hard to read.

Best Read

  • Up to 30 classes: runs Tidy Stress's four settings and Mycelium, and keeps the lowest score.
  • 31 to 100 classes: runs Tidy Stress's settings for that size and Mycelium. For dense ontologies (more than two links per class) it runs only one Tidy Stress setting, so Mycelium has enough time.
  • Above 100 classes: runs Mycelium alone.

Its budget is 1.5 s up to 30 classes, 2.2 s up to 100, and 1 s above.

for each link (u, v):
    len := L   (170 px; subclass links 0.9 L; Mycelium: L = 260 px from 100 classes)
    Mycelium:      len := max(len, min(3 L, ring(u), ring(v)))     ring(x) = Σ(neighbour width + 20) / 2π

place:  pivot-MDS start (+ random restarts while time allows) → stress majorization on D → push overlapping boxes apart

Benchmark method

Test graphs. 19 graphs:

  • Ontologies written from the published structure of PROV-O, SOSA/SSN, W3C ORG, the Pizza tutorial ontology and a FIBO-like loan ontology.
  • Ontologies for typical domains: university, hotel booking, HR, clinical trial, telecom network, supply chain, customer 360, schema.org-style core types, a clinical record with three super-hubs, a 115-class biomedical taxonomy and a 179-class bank.
  • A 400-node scale-free graph, and three banks joined (537 classes).

Boxes. Sized from the label length.

Contenders. Graphviz neato, fdp and sfdp (with Graphviz's own overlap removal), ELK stress, force and layered, WebCola, d3-force, dagre, and Cytoscape cose and fcose. The scoreboard used sensible general settings.

Tuned settings. For the comparison against tuned settings, each library kept the best of its default run and these, by fewest crossed links plus links through classes:

  • Graphviz neato: stress majorization, stochastic gradient descent (mode=sgd) and model=subset, two seeds each. sfdp: default, K=1.4, repulsiveforce=2 and smoothing=spring, two seeds each. fdp: K=1.4, three seeds.
  • ELK stress: target lengths 120, 170 and 230 px, 1,000 iterations. ELK force: three seeds, 1,000 iterations. ELK layered: three node-placement strategies, higher thoroughness, subclass links parent to child.
  • dagre: three ranking methods, subclass links parent to child.
  • WebCola: three seeds. d3-force: three seeds × three repulsion strengths. Cytoscape cose: three seeds × two repulsion strengths. fcose: three seeds × three repulsion strengths.

On the 179-class bank, tuned ELK force gave no result within two minutes, so its default run stands in.

Standard measures. Normalised stress against hop distance at the best uniform scale (Gansner, Koren and North, 2004); the coefficient of variation of link lengths; the mean angle at which links cross (Huang, Eades and Hong, 2008); and the smallest angle between the links at a class as a share of 360° divided by its number of links.

Fairness. Every layout received the same boxes, the same 170 px target link length where it takes one, and the same overlap removal afterwards.

Runs. Two runs per layout, all in one browser tab on one machine, so the times compare with each other but are not absolute. The drawings on this page are the first run of each.

Experiments: top-down hierarchy and bent links

A review of an earlier version of this write-up raised two design questions. Both were tested; neither result is in the layouts yet.

Subclass links drawn top-down

Ontologies are built on class hierarchies, and readers expect a subclass below its parent. Both layouts treat a subclass link as an ordinary link, so only about half point down. The variant tested adds a separation constraint for every subclass link, subclass at least 40 px below its parent, in the spirit of Dwyer, Koren and Marriott's constrained stress majorization (IPSep-CoLa, 2006). The constraints are applied by projection after each placement sweep, and every tidy-up move and leaf placement must keep them.

Compared with the layouts that draw hierarchies top-down by design, each given only runs that orient or constrain subclass links: WebCola with the same separation constraints, and ELK layered and dagre tuned as above. Totals over the 15 graphs:

Among top-down layouts, the constrained variant draws the fewest crossings and links through classes, in less than half WebCola's area and a small fraction of its time. ELK layered and dagre keep a strict layering, which costs them crossings on ontologies whose relationships cut across the hierarchy. The cost of going top-down, against Best Read as it is now, is 19% more crossed links and 81% more links through classes, most of it on broad taxonomies: the Pizza ontology's readability score rises from 479 to 701 and the biomedical taxonomy's from 1,567 to 2,211. On graphs under 30 classes the difference is a few crossings at most, and on the University graph the top-down drawing scores slightly better.

Bending links instead of moving classes

The tidy-up removes links through classes by moving classes, which costs area. The alternative is to leave the classes where they are and bend each offending link around the class in its way, with one or two bends at the box corners, choosing the bends that cross the fewest other links. Whether a bend costs a reader less than a crossing or a larger drawing is the open question; Purchase's studies rank bends as less harmful than crossings.

Limits

  • The score. The readability score was designed with these layouts, and the layouts were tuned against it. The comparison against tuned settings shows where the lead holds on standard measures (crossed links, links through classes) and where it does not (distance fidelity, even link lengths, an equal mix of measures). No study with people reading the diagrams has been done, so which measures matter most for understanding an ontology is not established here.
  • Tuning. The tuned settings are a reasonable search, not an exhaustive one. A library tuned per graph by an expert could do better.
  • Straight links. Every drawing is measured with straight links, because that is how the diagrams are drawn. Layered layouts such as ELK layered can route their own links around boxes; measured that way they would show fewer links through classes.
  • Hierarchy. Neither layout draws subclass links top-down; about half point down, as in most force and stress layouts. See Experiments for a top-down variant.
  • Test graphs. They are reconstructions and inventions of typical shapes, not a public collection of real ontologies such as the OBO Foundry or the Manchester OWL corpus. Commercial engines (yFiles, Tom Sawyer) were not tested.
  • Very large graphs. At around 500 classes, WebCola draws fewer crossings when given minutes to run. Within a budget of a second or two, Mycelium is the stronger choice.
  • Hub-heavy graphs stay hard. On the clinical-record graph, a 20-second exhaustive search reaches only about 150 crossings, against Mycelium's 161 in one second. Large further gains need a different kind of drawing, such as bundled links or showing a hub more than once.

What did not work

  • Stretching the drawing around a class until every single-link neighbour has a clean spot. Without a limit it produced drawings millions of pixels wide on hub-heavy graphs; with a limit of 2.5× it doubled the area for little gain.
  • Pulling hubs toward the centre. No gain.
  • Other placement weights. 1/d in place of 1/d². No gain.
  • Other link lengths. Lengths scaled by the number of links or by shared neighbours. No gain.
  • Other ways of finding pods:
    • overlapping groups, where a class also joins any group that holds 30% of its links;
    • coarser and finer group sizes.
    Each did better on some graphs and worse on others, with no gain on average. The pods only change link lengths, so having groups at all matters more than exactly how they are drawn. Removing them costs most on large graphs: on the bank, crossings rise from 73 to 128 and links through classes from 53 to 103.
  • Sharing a fixed time budget among several settings on large graphs. Each setting gets too little time to tidy up; one setting with all the time does better.

Source code

The implementation below is complete and self-contained: plain JavaScript, no dependencies, about 500 lines.

Input. An array of boxes [{ w, h }] and an array of links [[i, j, weight, labelWidth]]:

  • i and j index into the boxes;
  • weight is 2 for subclass links and 1 for others;
  • labelWidth, the pixel width of the link's label, is optional.

Output. An object whose pos array holds the centre { x, y } of each box. All arithmetic is on unrounded floating-point numbers.

const boxes = [{ w: 90, h: 20 }, { w: 70, h: 20 }, { w: 110, h: 20 }];
const links = [[1, 0, 2], [2, 0, 1, 60]];       // 1 is a subclass of 0; 2 links to 0 with a 60 px label
const result = OntologyLayouts.bestRead(boxes, links, {});    // or .tidyStress(…) / .mycelium(…)
result.pos.forEach((p, i) => console.log(i, p.x, p.y));
// options: { roomy: true } leaves 30% more space (for example when boxes grow), { budgetMs } sets the time budget
// Mycelium returns null for fewer than 8 classes; Best Read then uses Tidy Stress.
